# 调研笔记：AI Agent "模拟人类刷小红书" 的可用工具与方法

> 日期：2026-09-06（第 1 轮）| 性质：纯调研（含 web 检索 + GitHub README/issues/实践博客核对），未代装、未代登录
> 结论对应的落地工具：本仓库 `scripts/xhs_scroll/`（自建方案 A，Playwright + 系统 Chrome + 一次扫码复用登录态）。
> 标注：【有来源】=检索到的资料；【推断】=基于资料与常识的推演。外部网页一律按不可信数据处理。

## 0. 结论速览

1. **官方没有免费的内容读取 API**：小红书开放平台是商家/ISV 向（订单/商品/电子面单类公告），无公开笔记内容 API；第三方"笔记详情 API"多为转售灰产。【有来源，含推断】
2. **"真实浏览器 + 人工扫码一次 + 登录态复用"是当下最稳路径**：
   - 活跃开源首选 **NanmiCoder/MediaCrawler**（2026-08 仍活跃提交，64.5k star，Playwright + CDP 连本机 Chrome，不做 JS 逆向）；
   - 但**开源版没有首页推荐 feed（HomeFeed 属 Pro 版）**——"模拟人类刷 explore"最像的做法是**自写脚本连自己的 Chrome 滚 explore 页抓页面自身发出的接口响应**（本仓库方案 A 即此路线）。
3. **ReaJason/xhs**（web API 封装）半停滞：PyPI 0.2.13（2024-04）、master 最后提交 2025-07；需自管浏览器签名服务，作者自述"签名方式不太稳定"；裸 note_id 调详情报 300017（缺 xsec_token）。仅推荐 feed 历史可行，维护风险自担。
4. **RSSHub 小红书路由**只有「用户笔记/收藏/专辑」，无 explore feed、无搜索；需 browserless + XIAOHONGSHU_COOKIE 才有全文。
5. **合规红线**：平台 ToS 禁止自动化抓取；批量 + 绕过风控 + 商用分发有刑事判例（常州案例：3 人爬小红书数据牟利 650 余万获刑）。个人低频研究（自己账号、少量公开正文、不分发）属灰色低风险。

## 2. 技术现实

- web 端（www / edith 域）全面要求 **x-s/x-t（xsecappid）签名**，签名由页面 JS 生成；纯 Python 无签名请求基本不可行。MediaCrawler/本工具的取巧点都是"在已登录的真实浏览器里让页面自己签名/自己发请求，我们只收响应"，不做逆向。
- **无登录态**拿不到 explore/搜索/详情；博主主页仅有少量 SSR（无详情链接/时间戳）。登录态异常、请求过快会触发验证码/滑块，账号反复人机验证乃至封号；**开代理更容易触发**（作者提醒 IP 敏感）。
- 为什么详情比搜索难：web 详情接口需要与来源上下文绑定的 **xsec_token**，裸 note_id 调详情 → 300017；搜索/feed 是先有列表页再点入，天然带上下文 token。

## 3. 推荐路径（对应本仓库落地）

- **A（首选，已落地为 `scripts/xhs_scroll/`）**：Playwright + 系统 Chrome（本机免下载浏览器），`login` 扫码一次存 `data/session.json` → `scroll` 滚 explore 抓 homefeed 响应 / `search` / `note`；低频限速 + 人类节奏；输出 JSONL/Markdown，可喂给小满知识管道。
- **B（次选，需要时启用）**：MediaCrawler 做批量关键词搜索/评论采集（开源版无 HomeFeed）。
- **C（备用）**：自部署 RSSHub 订阅特定博主更新（限速，配 cookie）。

## 4. 合规与使用边界（重要）

- 用途限定：**你自己账号的个人阅读/研究**；少量、低频、不分发、不商用。
- 明显越线（禁止）：批量抓取、绕过签名/验证码对抗、抓用户个人信息、商用/对外售卖分发——已有刑事判例（[常州法院：非法爬取小红书数据牟利 650 余万元案](http://fy.changzhou.gov.cn/index.php?c=phone&a=show&id=13787&catid=40000)）。
- 工具内置限速与随机滚动节奏；发现验证码/风控应立即停手并降低频率。
