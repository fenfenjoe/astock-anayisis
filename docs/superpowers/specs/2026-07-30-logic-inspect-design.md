# 逻辑巡检定时任务 — 设计规格

> 状态: ✅ 设计已确认
> 日期: 2026-07-30
> 关联: CHAT.md §逻辑巡检

## 一、目标

在每日复盘自动化工作流中增加"逻辑巡检"能力，每天 17:00 系统性地检查文件内容合理性和一致性，发现问题自动生成 BUG 单，阻断"使用中才发现问题"的模式。

## 二、架构

```
task_schedule.json (新增 2 条)
├── ① logic_inspect  17:07 每天 → auto_logic_inspect.md
└── ② pending_remind 每2h:13  → auto_pending_remind.md

auto_logic_inspect.md (12+ 巡检条目)
├── 内容准确性检查 → 文件系统 + LLM 语义审查
├── FAIL → 创建 BUG 到 bugs/open/
├── 需用户确认 → 追加到 PENDING_CONFIRMATION.md
└── PASS/WARN → 写入执行日志

auto_pending_remind.md
├── 读取 PENDING_CONFIRMATION.md
├── 有待确认项 → 醒目输出提醒
└── 无则静默跳过
```

## 四、巡检条目（14 条，5 组）

### A 组：归档完整性（2 条）

| # | 巡检项 | 检查方式 | 交易日 | 非交易日 |
|---|--------|---------|:---:|:---:|
| A1 | `archive/{today}/早盘分析-staging.md` 存在 | 文件存在性 | ✓ | ✓ |
| A2 | `archive/{today}/复盘分析-staging.md` 存在 | 文件存在性 | ✓ | ✓ |

### B 组：Staging 章节对齐（3 条）

> Staging 文件由收盘复盘（`auto_evening_review.md` §9.1/§9.2）生成，为次日早盘/复盘提供日期特定数据输入。巡检验证 staging 章节结构与 `harness/prompts/` 模板的输入要求一致。

#### B1：`staging/今日-早盘分析.md` 章节对齐

参照 `auto_evening_review.md` §9.1 定义的结构，必须包含以下 8 个章节（每节非空、含实际数据行）：

| Staging 章节 | 供给模板章节 | 检查要点 |
|-------------|-------------|---------|
| 一、昨日盘面回顾 | `早盘分析-模板`§四 宏观研判 | 含指数涨跌+日内走势+核心矛盾概括 |
| 二、当前持仓快照 | `早盘分析-模板`§一 我的持仓 | 每只标的含代码+数量+成本价+前日收盘+浮盈% |
| 三、7维打分（非持仓板块） | `早盘分析-模板`§五 板块机会扫描 | 至少预留评分框架（数据由翌日早盘填入） |
| 四、各持仓做T建议 | `早盘分析-模板`§六 持仓映射 | 逐只给出做T方向+触发条件+风控，或标注"今日不做T" |
| 五、跨品种联动约束 | `早盘分析-模板`§七 操作清单 | 含已验证联动规则+校准参数+验证状态 |
| 六、前次预测回顾 | `早盘分析-模板`§八 上期预判回顾 | 逐条对比前日预测vs实际+准确率统计+根因标注 |
| 七、核心聚焦议题 | `早盘分析-模板`§四 宏观研判 | 3-6条具体可验证假设，非泛泛"关注大盘方向" |
| 八、今日信号汇总 | `早盘分析-模板`§九 每日信号生成 | 预定义信号含完整触发条件+有效时段+仓位 |

**FAIL 条件**：任一章缺失、章节内容为空（如持仓表只有表头无数据行）、日期指向错误。

#### B2：`staging/今日-复盘分析.md` 章节对齐

参照 `auto_evening_review.md` §9.2 定义的结构，必须包含以下 5 个章节：

| Staging 章节 | 供给模板章节 | 检查要点 |
|-------------|-------------|---------|
| 一、我的持仓（基线快照） | `复盘分析-模板`§一 我的持仓 | 含代码+数量+成本价；标注"此为明日复盘基线" |
| 二、今日核心回顾 | `复盘分析-模板`§五 上交易日核心回顾 | 含核心特征(1句概括)+核心教训(≥2条可操作)+明日核心变量(≥3个具体变量) |
| 三、特别关注项 | `复盘分析-模板`§四 今日任务 | 3-6条具体关注项，含触发条件和影响路径 |
| 四、跨品种联动约束（最新版） | `复盘分析-模板`§四 今日任务 | 含校准参数和验证状态，标注新增/修改项 |
| 五、前次预测评估 | `复盘分析-模板`§四 今日任务 | 逐条预测vs实际+准确率+根因，供明日Generator-Evaluator |

**FAIL 条件**：任一章缺失、核心教训<2条或为泛泛之谈、核心变量<3个或模糊不清、持仓基线为空。

#### B3：ETF 代码-名称交叉校验

交叉比对 staging 两个文件中出现的 ETF 代码→名称映射是否与 `config/持仓.md`（权威来源）一致。**必须机械化比对，不依赖人工目视。**

| 检查项 | 方法 |
|--------|------|
| 提取 `config/持仓.md` 中 code→name 映射（权威） | Python 逐行解析 |
| 提取 `staging/今日-早盘分析.md` 中所有 code→name | Python 逐行解析 |
| 提取 `staging/今日-复盘分析.md` 中所有 code→name | Python 逐行解析 |
| 比对：staging 中的 name 必须与 config 一致 | 严格字符串匹配 |

**FAIL 条件**：任何代码在 staging 中的名称与 config 不一致（如 159227 写成"恒生科技ETF"而非"航空航天ETF"）。

### C 组：报告章节对齐（4 条）

> 报告由早盘/复盘 Agent 根据 staging prompt + 模板生成。巡检验证报告产出章节与模板定义的输出结构一致。

#### C1：`reports/{today}/早盘报告.md` 章节对齐

以 `早盘分析-模板.md` 定义的产出结构为基准：

| 必须章节 | 来源模板 | 检查要点 |
|---------|---------|---------|
| 一、我的持仓 | §一 | 从 staging/config 填入的持仓表，至少含代码+名称+数量 |
| 宏观研判 | §四 | 含大盘方向判断+核心矛盾+反面情景推演+数据时区校验 |
| 板块机会扫描（非持仓） | §五 | N≥3个板块+七维评分表+建仓建议分类(🟢🟡🔴) |
| 持仓映射与操作判断 | §六 | 逐只七维评分+做T建议表+做T纪律勾选 |
| 操作清单 | §七 | 优先级排序+核心关注时间表+跨品种约束检查 |
| 上期预判回顾 | §八 | 逐条预判vs实际+根因+今日改进 |

**FAIL 条件**：任一章缺失、板块扫描<3个、持仓逐只分析遗漏标的、做T建议表为空。

#### C2：`reports/{today}/每日信号.md` 章节对齐

以 `早盘分析-模板.md` §九 定义的输出结构为基准：

| 必须节 | 检查要点 |
|--------|---------|
| 信号总表 | 非空，含优先级+标的+触发条件+操作类型+状态+紧急度+有效时段+信号ID |
| 信号触发记录 | 表存在（交易日盘中可能为空，复盘后应有数据） |
| 盘中验证记录 | 表存在 |
| 信号评价（复盘时填入） | 复盘完成后不可为空（交易日）；含决策质量+执行质量+入场/出场价+P&L+紧急度校准 |
| 当日信号统计 | 复盘完成后不可全为"—"，必须填具体数字（含早盘生成数/已触发/已执行/已过期/P0执行率等） |
| 信号收益追踪（复盘时填入） | 复盘完成后含本日结算信号+累计追踪统计+按优先级P&L |
| 信号与早盘报告对照 | 每条信号标注对应早盘章节+原文摘要 |

**FAIL 条件**：信号总表为空、复盘完成后信号评价表无数据行、统计表多项为"—"、信号与报告对照缺失。

#### C3：`reports/{today}/复盘报告.md` 章节对齐

以 `复盘分析-模板.md` §四（今日任务）定义的产出结构为基准：

| 必须章节 | 来源模板 | 检查要点 |
|---------|---------|---------|
| 一、我的持仓 | §一 | 使用最新同步后的持仓数据，含今日操作列 |
| 大市表现复盘 | §四.1 | 含三大指数+成交量+北向+涨跌家数+领涨/领跌板块 |
| 持仓复盘 | §四.2 | 逐只涨跌幅(标准口径)+开盘缺口+日内波动+操作建议；含做T复盘+信号执行复盘 |
| 早盘预判复盘 | §四.3 | 含方向预测准确率表+错误归因+板块扫描复盘+做T预判复盘 |
| 信号遗漏五问 | §四.2c | 五个必答问题全部有明确"有/无"结论+详情 |
| 经验沉淀 | §四.4 | 确认写入experience/的条目 |
| 持仓变更 | §四.5 | 列出新增/移除/变更（如有） |
| 次日Staging生成确认 | §四.6 | 确认两个staging文件已生成+归档+校验通过 |
| 信号收益追踪 | §四.2d | 含本日结算信号表+累计统计+按优先级P&L |

**FAIL 条件**：任一章缺失、信号遗漏五问未全部回答、持仓复盘遗漏标的、早盘预测对比无准确率统计。

#### C4：报告产出与 task_state 一致性

| 检查项 | 方法 |
|--------|------|
| task_state 中 morning_analysis=completed → 早盘报告.md + 每日信号.md 必须存在 | Python + bash 验证 |
| task_state 中 evening_review=completed → 复盘报告.md 必须存在 | Python + bash 验证 |
| task_state 中 evening_review=completed 但 staging_generated 字段为空 → WARN | JSON 字段校验 |

### D 组：数据一致性（3 条）

| # | 巡检项 | 检查方式 |
|---|--------|---------|
| D1 | `config/持仓.md` 与 `每日调仓.md` 持仓一一对应（代码+数量+成本一致） | 逐行比对 |
| D2 | `task_state.json` 的 date 字段 = today，trading_day 字段正确 | 值校验 |
| D3 | `signal_tracking.json` 无孤立信号 | 交叉检查 |

### E 组：经验与元数据健康（2 条）

| # | 巡检项 | 检查方式 |
|---|--------|---------|
| E1 | `experience/` 下三份文件无内容矛盾 | LLM 语义审查 |
| E2 | `BUG_INDEX.md` 统计数与 `bugs/open/`、`bugs/closed/` 实际文件数一致 | 计数比对 |

## 五、PENDING_CONFIRMATION.md 机制

### 5.1 文件位置

`my_doc/每日复盘/harness/automation/PENDING_CONFIRMATION.md`

### 5.2 格式

```markdown
# 待确认事项

> 由逻辑巡检自动维护。用户确认后在事项行末标注 `✅已确认` 或 `❌驳回`。

## 待确认 (N)

| # | 日期 | 来源BUG | 事项 | 优先级 | 截止时间 |
|---|------|---------|------|:---:|---------|
| 1 | MM-DD | BUG-XXX | 具体问题描述 | P1/P2/P3 | +N天 |

## 已确认 (M)

| # | 日期 | 来源BUG | 事项 | 结果 | 确认日期 |
|---|------|---------|------|------|---------|
```

### 5.3 生命周期

```
巡检发现 FAIL → 判断是否需要用户确认
  ├── 确定性修复 → 直接创建 BUG (auto_fix_eligible=true)
  └── 需用户判断 → 创建 BUG (auto_fix_eligible=false, MANUAL_REVIEW)
                    + 追加到 PENDING_CONFIRMATION.md 待确认表
```

- 用户确认后在行末标注 `✅已确认` 或 `❌驳回`
- 已确认项移到 `## 已确认` 表
- auto_pending_remind 仅扫描 `## 待确认` 表中的活动项

### 5.4 通知节奏

`auto_pending_remind` 每 2 小时（9:13, 11:13, 13:13, 15:13, 17:13, 19:13, 21:13）执行：

- 读取 `PENDING_CONFIRMATION.md`，统计 `## 待确认` 表中行数
- N > 0 → 醒目输出: `⚠️ {N} 项待确认事项，请查看 PENDING_CONFIRMATION.md`
- N = 0 → 静默跳过，输出 `OK | 无待确认事项`

## 六、BUG 创建规则

### 6.1 BUG 写入

巡检发现 FAIL → 按 `bugs/BUG_TEMPLATE.md` 模板创建 BUG 文件：
- 写入 `bugs/open/BUG-{NNN}.md`
- 更新 `bugs/BUG_INDEX.md`

### 6.2 auto_fix_eligible 判断

| 场景 | auto_fix_eligible | 状态 |
|------|:---:|------|
| 文件缺失但可从 staging 重新生成 | true | OPEN |
| 计数不一致（可自动修正） | true | OPEN |
| 内容质量/语义矛盾 | false | MANUAL_REVIEW |
| 需要用户决策 | false | MANUAL_REVIEW |
| 涉及金融计算/信号逻辑 | false | MANUAL_REVIEW |

### 6.3 去重

创建 BUG 前检查 `BUG_INDEX.md` 中是否已有相同问题（同文件+同类 FAIL），有则更新已有 BUG 而非新建。

## 八、交易日 vs 非交易日行为

逻辑巡检每天 17:07 运行，但检查范围和预期不同：

### 交易日

全部 5 组 14 条检查，所有 FAIL 按 §六 创建 BUG。

### 非交易日

仅执行 **A、B、D2、E** 组（跳过 C 组报告检查 + D1/D3）。

**非交易日预期校准**：

| 组 | 非交易日行为 |
|----|-------------|
| A | archive/{today} 预期**不存在**。MISSING → PASS；EXISTS → WARN |
| B | staging 文件预期**存在但日期可能为旧**（来自上个交易日复盘）。章节结构正常检查，日期为旧 → WARN 而非 FAIL。B3（代码-名称校验）正常执行 |
| D2 | task_state.date 可能指向上个交易日 → WARN |
| E | 正常检查，无特殊处理 |

**核心原则**：非交易日不因"没有做交易日本该做的事"而报 FAIL。WARN 提示状态滞后，不阻塞。
