## 一、背景与问题

### 1.1 现状

每日复盘 Harness 的定时任务（Windows 计划任务 `dsh-trigger-*` → `dsh_trigger.py` → 独立 `dsh --profile headless` 进程）执行早盘分析、盘中检查、收盘复盘。其中**经验沉淀目前完全依赖"显式写文件"**：

| 任务 | 当前经验机制 |
|------|------------|
| 早盘分析 `auto_morning_analysis.md` | 无独立沉淀步骤；仅"前次预测回顾"应用上期教训（从 staging 读） |
| 盘中检查 `auto_intraday_check.md` | **无任何经验沉淀** |
| 复盘分析 `auto_evening_review.md` | 第九步"经验沉淀"：显式要求写 `harness/experience/{投资经验,短线机会经验,报告审阅经验}.md`；5.4 异动扫描沉淀追加到投资经验.md |
| 经验维护 `auto_experience_health.md`（周三） | 检查经验文件大小/重复/矛盾/过时/章节完整性 |
| 信号质量周报 `auto_signal_quality_weekly.md`（周三 16:30） | 从 `signal_tracking.json` 统计周度信号指标 → 写入 `reports/weekly/信号质量周报.md` + 沉淀经验到投资经验.md |

**信号相关现状（已核实）**：
- 每日信号以 **markdown 12 列表格** 存在于 `reports/{date}/每日信号.md`（早盘生成 → 盘中原地更新 → 复盘回填评价/统计）。
- dashboard `view-signals` 页通过 `/api/daily-signals` 读取 markdown → `_parse_signals()` 解析为表格展示；**页面无信号质量评估内容**。
- 信号效果统计：`signal_tracking.json`（25 字段结构化记录，`lib/signal_tracking.py` 解析/结算）+ `lib/signal_quality.py`（8 项质量指标）——**统计逻辑已有，但只在复盘报告（7.6.4）和周报里渲染，dashboard 页看不到**。

**"认识小满"页现状（已核实）**：
- dashboard `view-agent` → "认识小满" tab（`agent-pane-profile`），由 `/api/agent/profile` 提供数据，`agent.js:renderProfile` 渲染。
- "爱逛的地方"（`xm-sites`）：`api_agent.py:_SITE_HOME`（财联社·电报、华尔街见闻、知乎热榜、雪球·今日话题，从 `config.RSS_FEEDS` 过滤）+ 自定义启用素材源；渲染为**纯文字链接**（名称 + kind），**无图标**。
- 小满访问渠道：RSSHub（`config.RSSHUB_INSTANCES`：rsshub.app / rsshub.rssforever.com）；`RSS_FEEDS` 现含 财联社/华尔街见闻/知乎/雪球，**无微博、小红书、X**。

**用户痛点（原文转述，v1.1 汇总）**：
1. 现在的机制"太机械化"——显式在定时任务 prompt 中写明"将经验写进文件"；
2. 希望小满有一个**"思考"机制**：执行早盘/盘中/复盘分析时，能从分析中**总结经验并与久经验融会贯通**；
3. 这些经验都是**量化经验**，未来还会通过**浏览论坛文章、阅读量化书籍、与用户交谈**等渠道加深；
4. 记忆和经验要写入**小满的记忆（OpenViking）**，替代当前的"学习"模块（文件）；
5. **分析前也要用经验**——早盘/盘中/复盘分析前，应从 OpenViking 注入量化分析相关经验；
6. **冲突处理原则**："当经验与事实违背时，面对冲突最理性的做法是贝叶斯更新——不彻底否定，也不彻底相信，而是调整概率"——此原则写入总结经验的原则；
7. **现存经验问题（曾提出，后移除）**：每日信号"总是喜欢止损"（下跌中卖出、上升中买入 = 追涨杀跌），而"低买高卖"才是正确理念——用户曾要求论证，v1.3 确认**不再需要论证**（见 §9.1）；
8. **每日信号数据结构化**：便于信号效果统计；结构化后**重新设计每日信号页**，并在页面增加**信号质量评估**内容。

### 1.2 关键架构事实（已核实）

- **定时任务运行时**：`dsh_loop_scheduler.py:build_cmd()` → `node bin.js --profile headless "执行 {prompt_file} 的全部内容"`，cwd 为仓库根，独立进程、零上下文累积。
- **headless profile**（`~/.dsh/profiles/headless`）只有 `@deepseek-ai/dsh-base` + `@deepseek-ai/dsh-headless`，**没有 memory plugin** → 定时任务 agent 目前无 viking 工具。
- **小满（dashboard agent）**：`etf-strategies/agent/dsh_runner.py` 以 `dsh --profile xiaoman` 运行，并显式设置 `OPENVIKING_PEER_ID=xiaoman` + `OPENVIKING_RECALL_PEER_SCOPE=actor`（小满记忆隔离在 peer `xiaoman`，只召回自己 actor 的记忆）。
- **web profile（本 GUI 会话）**：有 memory plugin（0.1.0），peer 默认按工作区派生为 `E--ideaworkspace-astock-anayisis`。
- **OpenViking 记忆结构**：`user/default/memories/{events,entities,experiences,preferences,trajectories,cases}/`；peer 级 `user/default/peers/{peer}/memories/`。Experience 类记忆格式为 **Situation / Approach / Reflect** 三段式。
- **memory plugin 能力**：会话开始自动 recall 注入 `<openviking-context>`；会话结束自动 capture+commit，后台提取长期记忆；提供 MCP 工具 surface（remember/search/find/read/list/grep/glob/add_resource/forget，另有 `search_experience`/`read_experience` 经验专用工具）。
- **经验文件的消费方**：`staging_templates.md`（复盘第十一步生成次日 staging 时注入"上期预判回顾/上期信号回顾"）、`早盘分析-模板.md`（第 205 行引用 `短线机会经验.md` 做纪律勾选）、`auto_logic_inspect.md` E1（检查三份经验文件无矛盾）。

## 二、设计目标（v1.3 更新）

1. **记忆入库**：早盘/盘中/复盘定时任务执行时的量化经验，自动写入 OpenViking（小满的记忆 = peer `xiaoman`），不再以"显式写文件"为主要沉淀手段。
2. **事件驱动的思考式沉淀**：沉淀不是"每次分析都写"，而是**事件驱动**——仅在 **① 发现新规律；② 旧经验被事实证伪** 时触发更新。沉淀过程遵循反思协议（检索 → 提炼 → 融会贯通 → 写入）。
3. **贝叶斯更新原则**：经验与事实冲突时，**不彻底否定也不彻底相信，而是调整置信度（先验→后验）**。此原则写入总结经验的原则，是反思协议冲突处理的核心。
4. **分析前经验注入（按领域过滤）**：早盘/盘中/复盘**分析之前**，从 OpenViking 注入/检索量化分析相关经验（**按当日分析领域过滤**，避免无关经验挤占上下文）。
5. **经验回流**：次日及以后的分析能**召回**这些经验（会话开始 `<openviking-context>` 注入 + 分析前显式检索）。
6. **小满聊天引入经验**（用户确认：引入）：小满与用户交谈时**主动引用量化经验**，聊天成为经验来源之一（来源=chat）。
7. **可扩展来源**：同一套"摄入管道"支持未来来源——论坛文章浏览、量化书籍阅读、用户交谈。
8. **每日信号结构化（数据入云库表，markdown 远期删除）**：每日信号从 markdown 表格升级为**云库表**（便于统计）；重新设计 dashboard 每日信号页并增加"信号质量评估"。
9. **认识小满页增强**：在"爱逛的地方"增加常见社交平台展示（微博/小红书/X/知乎/雪球），带 APP 图标（前端内置品牌 SVG）+ 可访问性状态（能访问→高亮，不能→置灰）；**可访问性判定结果存服务器缓存**（首次启动判定 + 小满真实访问时更新）；微博/小红书同时成为小满的**素材源**（Playwright 登录态采集，不走 RSSHub 路由）；**X 暂不做访问逻辑只保留图标**。
10. **用户待办回复页面（备忘，本期不实现）**：小满遇到需用户帮忙的地方（如社交平台需 Cookie、任务需用户选择）时，通过页面收集用户回复，小满据回复继续工作；待办去重。
11. **不破坏现有 harness 流程**：报告产出、staging 生成、信号追踪、Generator-Evaluator 分离等继续工作；经验文件远期彻底移除。

### 3.1 核心概念 1：反思协议（Reflection Protocol，事件驱动版）

替代"第九步：经验沉淀（写文件）"。**触发条件（用户确认）**：不是每次分析都写，而是**事件驱动**——当且仅当出现下列情况之一才触发更新：

- **T1 新规律**：今日分析中发现了**可复用、可操作、非一次性**的新规律（新市场模式/新信号形态/新数据陷阱等）；
- **T2 证伪**：今日事实**证伪或显著修正**了某条既有经验（早盘假设被盘中/收盘推翻、信号触发条件反复证伪等）。

两者皆无 → **本次不写**（复盘报告里记录"无新经验"一行即可，保持经验库纯净）。

触发后的四个子步骤：

1. **检索久经验（Recall，按领域过滤）**：以今日分析主题（板块/信号/做T/宏观/数据纪律等）为 query，`viking_search` 检索既有经验，**按领域过滤**（只召回与本次分析相关的领域，避免无关经验挤占上下文）。
2. **提炼（Distill）**：把触发本次更新的发现按经验 Schema（见 §5）结构化。T1 → 提炼新规律；T2 → 提炼证伪证据。
3. **融会贯通（Synthesize，贝叶斯更新）**：与检索到的久经验对比，判定关系：
   - `新建`：全新规律，无旧经验 → 新条目（置信度=中，先验）；
   - `确认`：久经验被今日验证 → 在该条目 Reflect 追加验证记录，**置信度上调**；
   - `调整`：今日证据与旧经验部分冲突/细化 → **不推翻**，按贝叶斯更新**调整置信度与适用范围**（记录证据链：何时/何事实/如何调整）；
   - `合并`：与旧经验同主题可归并 → 合并为一条更完整的（旧条目标记 merged）；
   - `冲突暂存`：证据不足/矛盾无法当场裁决 → 标记 `conflict`，**置信度下调但不删除**，留给周三经验健康任务/用户裁决。
4. **写入（Persist）**：按上一步结果写 OpenViking：
   - 新建/调整/合并 → `viking_remember`（category=experiences，内容按经验 Schema）；
   - 冲突暂存 → 在条目中标注 `conflict_with: <uri>` + 置信度下调。

> **贝叶斯更新原则（写入经验总结原则）**：
> "当经验与事实违背时，面对冲突最理性的做法是贝叶斯更新——不彻底否定，也不彻底相信，而是调整概率。"
> 落实到 Schema：每条经验带 `置信度`（高/中/低）+ `证据链`（每次验证/证伪记录）。一次证伪 ≠ 删除经验，而是置信度下调 + 适用范围收窄；多次证伪（置信度降至阈值）→ 才标记 `deprecated`。一次验证 ≠ 置信度打满，仍需多轮确认。

> 与旧机制的差异：旧机制 = "把经验追加到某文件某章节"（文件操作，每次复盘都写）；新机制 = "只在有新规律或被证伪时，想清楚与久经验的关系（含置信度调整），再决定怎么记"（认知操作 + 事件驱动）。

### 3.2 核心概念 2：分析前经验注入（Pre-Analysis Experience Injection，按领域过滤）

用户新想法：**早盘、盘中、复盘分析时也会使用经验，因此在分析前要从 OpenViking 注入量化分析相关的经验**（用户确认：按领域过滤）。

设计（叠加在 memory plugin 自动 recall 之上，显式化）：

| 环节 | 注入方式 |
|------|---------|
| 自动通道（无需改 prompt） | memory plugin 会话开始自动注入 `<openviking-context>`（按会话首条消息语义检索 peer xiaoman 记忆） |
| **显式通道（prompt 内新增一步）** | 每个定时任务 prompt 在**前置检查之后、分析开始之前**新增"经验注入"步骤：`viking_search` 检索与当日分析相关的量化经验，**按当日分析领域过滤**（早盘：市场判断/持仓板块/做T纪律/信号设计；盘中：信号验证/触发条件；复盘：预测回顾/信号复盘/异动扫描），取 top-N（如 5-8 条）纳入分析依据 |

- **领域过滤规则**：`viking_search` 的 query 明确携带领域关键词（如"做T纪律 信号设计"），或检索后按 `元数据.领域` 字段过滤，只保留与当日分析模块匹配的经验条目；避免注入"信号设计"经验给纯宏观研判等无关场景。
- 注入内容落到分析：早盘 → 板块扫描评分/做T纪律参考；盘中 → 信号验证/追加参考；复盘 → 预测回顾/信号复盘对账。

### 3.3 运行时打通（关键前置）

**现状**：headless profile 无 memory plugin，定时任务 agent 无法调用 viking 工具。

**方案**：
1. 给 headless profile 安装 memory plugin：
   ```bash
   dsh plugin --profile headless add @openviking/dsh-memory-plugin
   ```
   （与 xiaoman/web profile 相同；凭据解析沿用 `OPENVIKING_*` → `~/.openviking/ovcli.conf` → `ov.conf`，已有 ovcli.conf 无需额外配置）
2. **peer 归属（用户确认：默认写 xiaoman peer）**：定时任务经验写入 **peer `xiaoman`**（与 dashboard 小满同 peer）。原因：
   - 用户要求"写入小满的记忆"——小满 = peer `xiaoman`；
   - 同 peer 才实现"融会贯通"：小满聊天（actor scope）能召回定时任务沉淀的量化经验；
   - 定时任务自身（headless）也要能召回久经验 → 同样设 `OPENVIKING_PEER_ID=xiaoman` + `OPENVIKING_RECALL_PEER_SCOPE=actor`。
   - 实现：在 `dsh_loop_scheduler.py:dispatch()` / `dsh_trigger.py` 派发时注入环境变量（与 `dsh_runner.py` 的 `XIAOMAN_OV_ENV` 对齐）：
     ```python
     OV_ENV = {"OPENVIKING_PEER_ID": "xiaoman", "OPENVIKING_RECALL_PEER_SCOPE": "actor"}
     ```
3. **捕获策略**：定时任务 agent 的会话 capture 建议**开启但收敛**：
   - 保留 capture（每次分析会话本身就是"记忆"原材料，后台可提取事件/轨迹）；
   - 设 `captureAssistantTurns=true`、`captureMode=semantic`、`commitTokenThreshold` 保持默认（20000）——控制注入噪音；
   - 复盘这类长会话的产出（报告/staging）不入记忆，记忆只承载"经验条目 + 事件摘要"。

## 五、经验 Schema（量化经验条目结构）

OpenViking Experience 的 Situation/Approach/Reflect 三段式，扩展为量化经验专属字段（**置信度 + 证据链**，支撑贝叶斯更新）：

```markdown
# 经验标题（一句话：场景 + 结论）

## Situation（触发场景）
- 市场环境：{普涨/普跌/震荡/风格切换/外盘冲击...}
- 触发条件：{板块/信号/标的/数据形态的具体量化条件}

## Approach（应对方法）
- 分析动作：{早盘/盘中/复盘时怎么做}
- 操作纪律：{具体的可执行规则，含阈值/触发价/仓位}

## Reflect（验证与校准）
- 证据链：{每次验证/证伪记录，可多条。格式：{YYYY-MM-DD} {来源} {事实} {置信度调整}}
- 校准结论：{规律有效 / 需修正（收窄适用范围）/ 已证伪}
- 置信度：{高 / 中 / 低}（贝叶斯后验，随证据更新）

## 元数据（供检索与融会贯通）
- 来源：{morning_analysis | intraday_check | evening_review | signal_quality | forum | book | chat}
- 领域：{市场判断/跨市场映射/数据纪律/信号设计/做T/板块扫描/宏观/超跌反弹/...}
- 状态：{active | deprecated | merged | conflict}
- 关联：{相关经验 URI 列表}
- 首次沉淀：{YYYY-MM-DD} | 最近更新：{YYYY-MM-DD}
```

**贝叶斯更新的落地规则**：
- 新条目默认置信度=中；单次验证 → 中→高（不一次打满，需 2+ 次独立验证）；单次证伪 → 中→低（不删除）；低置信度再被证伪或 90 天无更新 → `deprecated`。
- 冲突双方都保留（不删旧），各标 `conflict_with`，由周三健康任务/用户裁决后再定去留。

> 写入时用 `viking_remember`（category=experiences）或经验专用工具；内容即上表。关键词（领域/来源/标的代码）自然进入语义索引，`viking_search` 可召回。

4. **可访问性判定 + 服务器缓存（用户确认）**：
   - **访问通道分类（用户确认）**：
     - **RSSHub 源**：财联社·电报 / 华尔街见闻 / 知乎热榜 / 雪球热帖 → 走 RSSHub 路由拉取（`config.RSSHUB_INSTANCES`）；

   - **判定依据**：
     - RSSHub 源：RSSHub 路由可达且能拉到 RSS → `reachable=true`；路由不可达/超时 → `reachable=false`；
     - Cookie 源（微博/小红书）：**有有效 Cookie 且轻量 HTTP 探测通过 → true；无 Cookie、Cookie 失效或探测失败 → false**；

   - **缓存机制（用户确认）**：
     - **服务器首次启动时做一次可访问性判定**，结果写入服务器缓存（`agent_metadata` KV 或新增 `platform_reachability` 表）；

| 品牌 SVG 图标使用不当 | 品牌方异议 | 仅作"链接入口"指名使用（nominative use）；用官方公开图标资源；不做商业化使用 |

| 小满聊天引用经验导致人设崩（语气太"专家"） | 聊天体验下降 | persona 说明"以朋友口吻带出经验"，引用要自然（"我最近复盘发现…"），非播报 |

| 前端重设计违反设计纪律 | 页面风格崩坏 | 按 CLAUDE.md 第五节流程：frontend-design → ui-ux-pro-max → 编码 → design-critique |

## 十二、验收标准

1. **注入**：headless 定时任务会话开头出现 `<openviking-context>`，内容含近期量化经验；早盘/盘中/复盘分析前显式检索经验（按领域过滤，日志/报告中可见引用）。
2. **事件驱动沉淀**：一次完整复盘后，仅在有新规律或被证伪时，`user/default/peers/xiaoman/memories/experiences/` 新增/更新条目；无事件的日子不产生新条目。
3. **贝叶斯更新**：同一经验被证伪一次后，置信度中→低（条目仍在，证据链记录）；再被证伪或 90 天无更新 → deprecated；被验证 2+ 次 → 高置信。
4. **融会贯通**：同一主题第二次复盘时，新经验与旧经验发生"确认（置信度上调）/调整（收窄）/合并"之一；`status` 正确流转。
5. **回流**：次日早盘 staging 或分析中引用了 OpenViking 经验（而非仅文件）。
6. **小满聊天**：小满在聊天中能引用量化经验（回复含"复盘发现/最近经验"类内容）；聊天中的可复用经验可沉淀（来源=chat）。
7. **兼容**：过渡期 `harness/experience/*.md` 镜像存在且与库一致；逻辑巡检 E1 通过；报告/staging/信号流程无回归（`pytest` 全绿）。
8. **降级**：模拟 OpenViking 不可达 → 主流程继续，经验暂存 `_pending.md`。
9. **信号云库化**：**历史 `signal_tracking.json` 信号已一次性迁移到云库（signal_id 保留、数量与字段核对一致）**；dashboard 读云库正常；云库统计与旧 `parse_signal_markdown` 结果一致（单测对比）；不做云库↔markdown 一致性校验（用户确认）。
10. **页面（信号）**：每日信号页展示云库结构化信号 + 信号质量评估（8 项指标 + P0 执行率）；`design-critique` 通过。
11. **页面（认识小满）**：爱逛的地方展示社交平台（微博/小红书/X/知乎/雪球）+ **前端内置品牌 SVG 图标**（加载失败回退默认）+ 可访问性高亮/置灰；**可访问性状态来自服务器缓存**（首次启动判定 + 小满真实访问后更新，抽查 2-3 个平台与实际情况一致）；**X 置灰展示（不实施访问逻辑）**；**小满进入"逛微博/逛小红书"状态时，Playwright 触发采集微博/小红书热点内容并浏览（素材入 agent_knowledge，source 区分），无 Cookie 时状态回退并提示**。
12. **扩展**：`viking_add_resource` 导入一篇论坛文章后，可检索到并从其中提炼出 experiences 条目（Phase 4）。
13. **备忘**：§9.5 用户待办回复页面已登记待办池（未实现，排下个版本）。
