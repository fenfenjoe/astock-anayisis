> 实现方式（用户确认）：火山 Supabase 版 Data API（PostgREST over HTTPS）——避开直连 Postgres 的 IAM 权限限制（`AccountPermissionDenied`），用 ServiceRoleKey 走 REST。

## 一、目标架构

```
公司电脑 / 家里电脑（可同时在线）
  dashboard 进程（FastAPI）
  agent 常驻进程（RSS/发文/状态机）
        │  全部经 Postgres 客户端（psycopg 直连 / Data API）
        ▼
  火山 Supabase 版 Postgres（云端权威）  ← 多进程/多机器并发由数据库锁/事务保证
        ▲
  可重建缓存（K线 parquet、回测 NAV 中间产物）留在本地或 TOS，不作为权威
```

关键原则：
- **权威数据全部上云 Postgres**：users / portfolio_* / scheduler_* / daily_reports / agent_*（会话、消息、文章、活动、知识、来源、观点、metadata）。
- **本地零权威文件**：不再有 agent.db / cache.db 作为"本地真源"；不保留 `DB_MODE=memory` 快照互覆机制。
- **可重建数据**（kline_daily、backtest_nav、strategy_metrics、daily_signals）属于外部数据/算法产物，丢了可重拉重算，放本地 parquet / 本地缓存即可（见数据分层）。**2026-09-07 追加：TOS 缓存层已一并下线**。

## 二、数据分层决策

| 类别 | 数据 | 权威位置 | 说明 |
|---|---|---|---|
| A. 账号与配置 | users | 云 Postgres | auth 密码 hash / 角色 |
| B. 组合账本 | portfolio_holdings / portfolio_trades / portfolio_meta / available_cash | 云 Postgres | 用户录入手工数据，不可再生 |
| C. 每日复盘 | daily_reports（markdown 正文）、scheduler_runs / task 状态 | 云 Postgres | 报告正文 markdown 直接存列（与现 `report_upsert` 相同）；本地 reports/ 为工作副本（TOS 归档已下线） |
| D. Agent 拟人 | agent_sessions/messages/articles/activities/knowledge/sources/opinions/metadata | 云 Postgres | 本次用户痛点的核心 |
| E. 行情缓存 | kline_daily | 本地 parquet / SQLite 缓存 | 外部 API 拉取，可重建，**非权威**（TOS 缓存已下线） |
| F. 回测产物 | backtest_nav / strategy_metrics / daily_signals | 本地或懒生成 | 策略代码可重算 |

> E/F 也可后续整体上云，但当前先最小化迁移面；如迁移后体验好再扩展。

## 三、云端 Schema 草案（Postgres）

沿用现 SQLite 表结构语义（snake_case、TEXT 时间戳保持 `YYYY-MM-DD HH:MM:SS` 以便迁移），建表清单：

```
users(id serial, username text unique, password_hash, display_name, role,
      is_active bool, created_at, last_login)
portfolio_holdings(id, code, name, shares, cost_price, updated_at)
portfolio_trades(id, trade_date, name, code, quantity, price, side, remark, created_at)
portfolio_meta(key text primary key, value text)
daily_reports(id, report_date, report_type, markdown text, status, generated_at, source_file)
scheduler_runs(id, task_id, window_key, trigger, run_time, status, pid,
               duration_sec, output text, completed_at)
agent_sessions(id, persona, title, created_at, updated_at)
agent_messages(id, session_id references agent_sessions on delete cascade,
               role, content text, sources text/jsonb, created_at)
agent_articles(id, title, summary, content text, topics jsonb, sources jsonb,
               status, kind, published_at)
agent_opinions(id, topic, opinion, article_id, created_at)
agent_knowledge(id, source, title, url text unique, summary, content text,
                viewpoint, emotion, memory, read_at, published_at, consumed bool, fetched_at)
agent_metadata(key text primary key, value text)
agent_sources(id, name, url, kind, note, enabled bool, created_at)
agent_activities(id, kind, label, source, started_at, ended_at, note, tokens)
```

- RLS：先内部单客户端（service/db 凭据）使用，RLS 默认开启 + 全部行归应用；后续如需多租户再细化。
- JSON 字段（sources/topics）用 `jsonb`，应用层序列化兼容。

## 五、分阶段实施

- **阶段 0（前置）**：Supabase workspace 登录 + 建库；本地临时 Postgres（或云 dev 库）跑通 `cloud_db.py` 骨架（TDD）。
- **阶段 1**：agent 权威数据（会话/消息/活动/知识/文章/来源/metadata）迁云——这是用户痛点域，优先闭环；agent/dashboard 双进程直连云库并发测试。
- **阶段 2**：portfolio / reports / scheduler 迁云。
- **阶段 3**：移除本地 SQLite 权威路径与 memory 快照机制；K线/NAV 明确为可重建缓存（本地 parquet/TOS）。
- **阶段 4**：双机真实验证（公司/家里同时开、互写互读）。

## 六、风险与回滚

- 云不可达/计费：应用 fail-fast + 明确报错；保留一键回滚到"本地 sqlite + cloud_sync"老分支的 tag。
- 迁移前必须**先备份**现有 cache.db/agent.db 快照（即使云端已空，本地表里仍有持仓/交易/报告/用户等价值数据——实测 cache.db 有 129 报告/272 scheduler_runs/持仓 5/交易 32/users 1，agent 全空）。
- 网络延迟：权威数据量小（报告正文除外的行数在千级），Postgres 直连可接受；E/F 大表不入云避免拖慢。

## 七、验收标准

1. 公司/家里两台机器启动 dashboard 后，「会话」与「做过的事」读到**同一份云数据**。
2. A 机器新建会话/聊天、产生活动 → B 机器（重启后）能看到。
3. 本地不再产生 agent.db/cache.db 权威副本；删除本地 data/ 后重启，数据仍在（云）。
4. 并发写（dashboard 写会话 + agent 写活动同时发生）不丢数据。
