- **实际行为**: 后台全量测试运行中 11 项 **FAILED/ERROR**（非 skip）：

  | tests/test_dashboard_db_cloud.py | 6 FAILED | `user_get_by_username` 返回 None / `meta_get` None / `len(hs)==0` 等 |

  根因（模块导入时序）：
  1. `cloud_db._ENABLED = bool(_URL and _KEY and requests is not None)` 是**模块导入时计算的常量**（cloud_db.py:25-27）；
  2. 后台任务进程已注入 `.env`（SUPABASE_URL/KEY 存在）→ skipif 判定「有凭据」→ 不跳过；
  3. 但若 `cloud_db` 在 `.env` 被 `dashboard/app.py` 的 `load_env_file()` 写入 os.environ **之前**已被导入（例如某些测试模块早期 import `agent/db.py`/`dashboard/db.py` 的 else 分支），则 `_ENABLED` 在那一刻被固化为 `False`，且**整个进程不再更新**；
  4. fixture `monkeypatch.setattr(agent_db, "USE_CLOUD", True)` 只改 USE_CLOUD 标志，改不了 `cloud_db._ENABLED` → 云操作走 fail-safe 空结果路径（select 返回 []、insert 返回 None）→ 断言失败。

  验证：在干净 shell（无 .env）`python -m pytest tests/test_agent_db_cloud.py tests/test_dashboard_db_cloud.py -q` → 11 skipped ✓；用 `.env` 加载后同一命令 → 11 passed（101s，真实连云）✓；仅在全量套件后台运行（导入顺序混杂）时出现 FAILED/ERROR → 确认是**导入时序 + skipif 门控不严**的测试隔离缺陷，非云功能本身缺陷。
- **复现步骤**:
  1. 在注入 `.env` 的环境运行全量：`cd etf-strategies && python -m pytest tests/ -q --tb=line` → 观察 test_agent_db_cloud ERROR（_cd_enabled False）+ test_dashboard_db_cloud FAILED
  2. 干净 shell 单跑：`python -m pytest tests/test_agent_db_cloud.py tests/test_dashboard_db_cloud.py -q` → 11 skipped（对照）
  3. `.env` 加载后单跑：`python -c "from load_env import load_env_file; load_env_file()"` 后同命令 → 11 passed（对照）
- **受影响文件**:

- **建议修复**: 二选一（需设计决策）：
  (a) `cloud_db.enabled()` 改为动态读取（`_ENABLED` 改为函数内每次 `os.environ.get`），消除导入时序依赖；
  (b) cloud 测试 skipif 增强为「无凭据 **或** 当前 backend 被 conftest 强制 file 时跳过」（如 `pytest.mark.skipif(not _cloud_ready(), ...)` 同时检查 `cloud_db.enabled()` 与 backend 标志），使测试环境确定性化。
