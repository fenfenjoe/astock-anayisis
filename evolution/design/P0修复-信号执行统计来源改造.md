# P0 修复：信号执行统计来源改造（信号-成交对账）

> 自进化框架运行前置修复（数据管道打通）
> 依据：用户反馈「我其实有执行，执行后从"持仓/资产"界面"录入交易"记录，但小满没从那统计」
> 方案（用户自定义）：**盘中分析、复盘时检查成交记录，有与信号对应的成交 → 信号已执行 → 更新信号状态**
> 日期：2026-09-24 | 状态：**已实施（对账 lib + 复盘 prompt 改造 + 真实数据验证）**

## 〇、实施结果（验收全部达成）

1. **根因最终定位**：复盘 prompt 旧的 7.6.1b 关联逻辑（2026-09-14）**只回填 entry_price/entry_time，从不把 status 置为 executed**——用户真实执行的信号在结算统计里永远算"未执行"（执行率恒 0）。
2. **对账 lib**：`lib/signal_reconcile.py`（纯函数，14 项测试）——匹配优先 **remark 信号 ID**（`执行信号 SIG-xxx`，用户录入时界面自动带），兜底同日+同码+同向；命中 → status=executed + entry_price + entry_time。
3. **复盘 prompt 改造**：7.6.1b 用对账逻辑替换旧逻辑，且**在 7.6.2 结算之前**执行（先标 executed 再结算）。
4. **真实数据端到端验证**：用本地 `每日调仓.md` 34 条交易 + 本地 `signal_tracking.json` 23 条信号对账 →
   ```
   matched=2 updated=2

   SIG-20260921-04: triggered -> executed entry_price=0.712
   SIG-20260921-06-盘中: triggered -> executed entry_price=0.866
   ```
   用户 9/21 的两笔真实执行**被正确识别并置为 executed**——之前"执行率 0%"纯属统计断点。
5. 全量测试 **636 passed, 1 skipped**（+14 项 signal_reconcile，无回归）。

**补充数据事实（调查中发现）**：
- 本地 `signal_tracking.json`（23 条）是**完整权威档案**；云库 `signal_tracking` 表（37 条）缺最新（9/21 信号不在云库，因 9/21 后复盘可能未跑/未同步）。
- `portfolio_trades`（云库）含 9/21 成交，但本地 `每日调仓.md` **也同源有**（Dashboard 录入写本地 + 云库镜像）——对账读本地 md 即可，无需依赖云库连接稳定性。
- `DASHBOARD_DB_BACKEND=cloud` 与 `AGENT_DB_BACKEND=cloud` 是两个不同环境变量（web 层 vs agent 层），cloud_db.py 在 etf-strategies/ 根。

## 一、根因（已查证）

两套系统、两个数据源、未打通：

```
用户真实操作                            小满信号系统
─────────────────────                 ─────────────────────
"持仓/资产"界面"录入交易"                signal_tracking（云库表 + 本地json）
  → portfolio.append_trade()             → 信号状态：open/triggered/executed
  → 写 每日调仓.md + 持仓.md             → 结算：settle_due_signals 只看 status
  → _sync_ledger_to_db()                 → P0a 分维度统计：账户级只看 executed
  → portfolio_trades（云库表）
      ↑ 用户真实执行在这里！                 ↑ 小满统计执行只看这里！
```

**证据**：
- `portfolio.append_trade()`（portfolio.py:664）：只写两个 md 文件，**无任何信号逻辑**
- `api_daily.py` 已有 `/signal-execute`（一键执行，手动调用）和 `/signal-entry`（复盘关联），但用户走的是**独立的录入交易界面**，不经过信号关联
- `portfolio_trades` 表结构：`trade_date / code / side(买入|卖出) / quantity / price / remark`
- `signal_tracking` 表结构：`signal_id / signal_date / ticker / trade_type(buy|sell) / status / entry_price / entry_time`

## 二、方案（用户确认）

**在已有调度任务（盘中检查 / 收盘复盘）中增加"信号-成交对账"步骤**：

```
盘中 14:30 / 复盘 15:52
  → 读当日信号（signal_tracking，signal_date=今日，status∈{open,triggered}）
  → 读当日成交（portfolio_trades，trade_date=今日）
  → 匹配（ticker=code ∧ 方向一致 ∧ 同日）
  → 命中 → 更新 signal_tracking：status=executed + entry_price=成交价 + entry_time=成交时间
```

**优势**（相对"录入时实时关联"）：
- 零侵入：不改 append_trade 录入链路，录入失败不影响信号
- 复用已有调度：当天多次对账（盘中 14:30 + 复盘 15:52），补录/晚录天然覆盖
- 信号状态变为真实反映 → P0a 统计、P0 检查点（REQ-007 6 检查点）全部恢复有效

## 三、匹配规则与边界

### 3.1 匹配键（两轮：精确优先 + 严格兜底）
| 轮次 | 键 | 规则 |
|------|-----|------|
| **1. remark 信号 ID**（优先） | 成交 `remark` 含 `执行信号 SIG-xxx` | 用户从界面录入交易时自动带，**最精确**；命中即锁定该信号 |
| **2. 严格键**（兜底） | `signal_date`==`trade_date` ∧ `ticker`==`code` ∧ `trade_type`↔`side` | 同日+同码+同向；已被 remark 占用的成交不参与兜底 |

匹配范围：信号 `status ∈ {open, triggered}`；已 executed/settled/partial_executed 不动（**终态保护**，复用 `cloud_update_fields` 既有逻辑）。

### 3.2 边界场景
| 场景 | 处理（第一版） |
|------|--------------|
| 一信号多成交（分批） | 取第一笔匹配成交，回填该笔价格 |
| 多信号同代码同方向 | remark 指定了具体信号 → 命中该信号；无 remark 按严格键（同日同码同向） |
| 补录（成交日≠信号日） | 严格键要求同日；跨日补录靠 remark 信号 ID 仍能命中（不依赖日期） |
| 撤单/改单 | 对账只增不改：一旦 executed 不降级（终态保护） |
| 数量不符 | 不校验数量（信号 shares 是建议量，实际成交可分批/部分） |

### 3.3 对账结果输出
每次对账写 `automation/logs/signal_reconcile_{date}.md`：
- 匹配成功列表（signal_id → 成交 code/price/time）
- 未匹配信号列表（当日有信号但无成交 → 维持 open，供 P0 检查点告警）
- 补录/异常标注
