# BUG-030: parse_signal_markdown 无法解析带括号注解的状态列（复盘入库解析 0 条）

- **组件**: lib/signal_tracking.py（_TRACKABLE_STATUSES 精确匹配）+ prompts/auto_evening_review.md 8.6.1
- **严重程度**: P1（高）
- **违反的正确性定义**: auto_evening_review.md §8.6.1「解析入库」——复盘时 `parse_signal_markdown` 必须从 `每日信号.md` 解析当日已触发信号并写入追踪库（云库优先）。2026-09-15 复盘实测**解析 0 条**（与盘中已入库的 6 条云库记录矛盾）
- **状态**: OPEN
- **auto_fix_eligible**: true
  - 判定理由：确定性修复（状态列剥离括号注解后精确匹配），不涉及金融计算口径
- **发现时间**: 2026-09-15T16:0x CST
- **发现方式**: 收盘复盘验证（第八步 8.6.1 入库解析实测）
- **来源 REQ**: N/A（BUG-012 同根因扩展：加粗剥离已修，括号注解未覆盖）
- **预期行为**: 状态列 `已触发（14:36 现价 8.817...）` / `已取消（显式放弃）...` / `已过期（窗口到期）...` 等**带括号注解**的状态词元，应剥离括号注解后与 `_TRACKABLE_STATUSES = {'已触发','已执行','部分执行'}` 匹配成功
- **实际行为**: `_strip_md` 仅剥离 markdown 加粗（`**`）标记（BUG-012 修复），未剥离括号注解 → 状态列 `已触发（14:36...）` 精确匹配 `已触发` 失败 → `parse_signal_markdown` 返回 0 条（2026-09-15 实测）。云库当日 6 条信号因盘中任务（source=intraday_check）已入库而未缺失，但复盘路径入库永远解析 0 条，破坏「复盘为入库兜底」的可靠性
- **复现步骤**:
  1. 读取 `reports/20260915/每日信号.md`（状态列含括号注解：`已触发（14:36 现价 8.817(-0.65%)...）`）
  2. 调用 `parse_signal_markdown(md_text, '2026-09-15')`
  3. 观察返回 `[]`（0 条），尽管云库已有盘中入库的 6 条当日信号
- **受影响文件**:
  - `lib/signal_tracking.py`（_strip_md：剥离 `**` 但未剥离括号注解；L395-400）
- **潜在影响**: 复盘 8.6.1 入库解析永远 0 条 → 若盘中任务未入库（如早盘无信号文件、盘中任务中断），复盘兜底入库失效 → 信号收益追踪/仪表盘数据缺失；与 BUG-012（加粗）同类根因，需一并覆盖
- **建议修复**: `_strip_md` 在剥离 `**` 后追加剥离括号注解（正则 `\s*（[^）]*）\s*$` 或首个 `（` 起截断），并新增单测覆盖「已触发（注解）/已取消（注解）/已过期（注解）」三种形态
